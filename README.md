### Задание 1. Резервное копирование

### Кейс
Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования. 

Необходимо описать, какие варианты резервного копирования подходят в случаях: 

1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.

1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.

1.3.* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.

*Приведите ответ в свободной форме.*

### Решение 1

#### 1.1 
Для такого сценария подходит полное резервное копирование.
- Суть: каждый день делается полная копия базы данных на момент окончания рабочего дня.
- Преимущества: легко восстанавливать данные, минимальный риск потери информации.
- Недостатки: требует много дискового пространства и времени на создание копии.

#### 1.2
Для таких задач нужны инкрементальные/дифференциальные бэкапы + журнал транзакций.
- Суть:
    - Инкрементальные — сохраняют изменения с момента последнего полного бэкапа.
    - Дифференциальные — сохраняют изменения с момента последнего полного бэкапа.
    - Журналы транзакций (binlog/MySQL, WAL/PostgreSQL) — позволяют восстановить данные до конкретного момента времени.
- Такой подход называется point-in-time recovery (PITR).

#### 1.3
Да, возможен и называется High Availability (HA) / репликация с автоматическим failover.
Варианты:
- Мастер-слейв репликация с failover (MySQL, PostgreSQL).
- Кластерные решения:
    - MySQL Group Replication, Galera Cluster
    - PostgreSQL Patroni + etcd/Consul


### Задание 2. PostgreSQL

2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).

2.1.* Возможно ли автоматизировать этот процесс? Если да, то как?

*Приведите ответ в свободной форме.*

### Решение 2

#### 2.1
Резервное копирование с помощью pg_dump:
```
pg_dump -U postgres -h localhost -F c -b -v -f /backup/mydb.backup mydb
```
Восстановление базы данных с помощью pg_restore:
```
pg_restore -U postgres -h localhost -d mydb_restored -v /backup/mydb.backup
```
#### 2.1*
Да, резервное копирование и восстановление можно автоматизировать.
1. Скрипты shell + cron (Linux)
2. Использование систем управления резервными копиями:
    - pgBackRest — утилита для автоматических инкрементальных и полных бэкапов PostgreSQL.
    - Barman — централизованное решение для резервного копирования и восстановления нескольких серверов PostgreSQL.

### Задание 3. MySQL

3.1. С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL. 

3.1.* В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?

*Приведите ответ в свободной форме.*

### Решение 3

#### 3.1
Для инкрементного бэкапа чаще используют binary logs вместе с mysqlbinlog.
1. Включение бинарных логов в MySQL (в my.cnf):
```
[mysqld]
server-id=1
log_bin=mysql-bin # включение бинарных логов
```
2. Сделать полное резервное копирование базы:
```
mysqldump -u root -p --all-databases --single-transaction > full_backup.sql
```
3. Инкрементное резервное копирование (копирование бинарных логов, которые создаются после полного бэкапа):
```
mysqlbinlog --read-from-remote-server --host=localhost --user=root --password=password --raw --result-file=/backups/mysql-binlogs/ mysql-bin.000001
```

#### 3.1*
- Резервное копирование большой базы может сильно замедлять работу мастера. На реплике бэкап выполняется в фоне, не мешая основной работе.
- На реплике можно делать консистентный бэкап с помощью mysqldump или xtrabackup, пока мастер обслуживает пользователей.
- Бинарные логи на реплике можно использовать для восстановления данных на любой момент времени, что удобно при ошибках или авариях.
- Если что-то пойдёт не так во время резервного копирования, мастер остаётся в безопасности, а реплику всегда можно пересоздать из свежего бэкапа.
